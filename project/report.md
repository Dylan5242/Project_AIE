Проект решает задачу прогнозирования нагрузки на веб-сервис: по истории HTTP-запросов за последние 168 часов формируется прогноз количества запросов на следующие 24 часа. Для обучения используется открытый датасет Calgary-HTTP. Результатом проекта является сохранённая ML-модель и FastAPI-сервис, предоставляющий прогноз через REST API.

## 2. Постановка задачи и контекст

### 2.1. Предметная область и задача

Нагрузка на веб-сервис изменяется в зависимости от времени суток и дня недели. Если заранее оценить количество запросов, можно планировать вычислительные ресурсы, настраивать масштабирование и выявлять периоды повышенной нагрузки.

Потенциальный пользователь решения — разработчик или инженер эксплуатации веб-сервиса. Типовой сценарий: передать в API почасовую историю нагрузки за последние семь дней и получить прогноз на следующие сутки.

### 2.2. Формулировка задачи в терминах ML

Задача относится к регрессии временных рядов. Вход модели — последние 168 почасовых значений `requests` и timestamp последнего наблюдения. На их основе строятся семь признаков:

- `hour` — час суток;
- `day_of_week` — день недели;
- `is_weekend` — признак выходного дня;
- `lag_1` — нагрузка час назад;
- `lag_24` — нагрузка сутки назад;
- `lag_168` — нагрузка неделю назад;
- `rolling_mean_24` — средняя нагрузка за последние сутки.

Выход модели — вектор из 24 чисел: прогноз `requests` для каждого часа следующих суток. Используется direct multi-output forecasting: модель сразу рассчитывает весь горизонт, а не выполняет рекурсивный прогноз.

Основные требования к решению:

- прогноз не должен использовать будущие значения временного ряда;
- результат должен формироваться достаточно быстро для синхронного HTTP-запроса;
- модель должна запускаться без GPU;
- отрицательные значения прогноза недопустимы и обрезаются до нуля.

### 2.3. Метрики качества

Для оценки используются три метрики:

- **MAE** — основная метрика. Показывает среднюю абсолютную ошибку в понятных единицах `requests/hour`.
- **RMSE** — сильнее штрафует крупные ошибки прогноза в часы пиковой нагрузки.
- **sMAPE** — показывает относительную ошибку в процентах и помогает сравнивать качество при разных уровнях нагрузки.

## 3. Данные

### 3.1. Источник данных

Используется открытый датасет [Calgary-HTTP](https://ita.ee.lbl.gov/html/contrib/Calgary-HTTP.html) из Internet Traffic Archive. Он содержит реальные HTTP-запросы к серверу факультета Computer Science Университета Калгари. Исходный лог хранится в `data/raw/calgary_access_log.gz`.

### 3.2. Структура данных

Скрипт `scripts/prepare_calgary_http.py` разбирает timestamp каждого запроса и агрегирует события по часам. Если в некотором часу запросов не было, добавляется значение `0`. Подготовленный файл `data/processed/calgary_http_hourly.csv` содержит две колонки:

| Колонка | Тип | Описание |
|---|---|---|
| `timestamp` | datetime | Начало часового интервала |
| `requests` | int | Количество HTTP-запросов за час |

После агрегации используются временные и числовые данные. Производные признаки также числовые: календарные значения `hour`, `day_of_week`, бинарный `is_weekend`, лаги и скользящее среднее. Текстовые данные, изображения и персональные данные в модель не передаются.

Характеристики набора данных:

- период: `1994-10-24 13:00:00` — `1995-10-11 14:00:00`;
- размер: 8 450 почасовых наблюдений;
- суммарное число запросов: 725 125;
- средняя нагрузка: 85,81 запроса в час;
- минимум и максимум: 0 и 956 запросов в час;
- часы без запросов: 167.

### 3.3. Предобработка и EDA

Подготовка данных включает загрузку архива, извлечение timestamp из строк лога, агрегацию по часам и заполнение отсутствующих часовых интервалов нулевыми значениями. Перед обучением данные сортируются по времени. Для табличных моделей строятся лаговые и календарные признаки, для LSTM — последовательности длиной 168 часов с нормализацией по статистикам train-части.

В `notebooks/model_experiments.ipynb` выполнен разведочный анализ:

- построен график временного ряда за весь период и за последние 14 дней;
- исследована средняя нагрузка по часам суток и дням недели;
- построена heatmap `day_of_week × hour`;
- проверены описательные статистики и количество нулевых значений.

EDA показывает заметную суточную и недельную сезонность. В ряду присутствуют 167 нулевых часов и отдельные пики до 956 запросов при среднем значении 85,81; они не удаляются, так как могут отражать реальное поведение сервиса. Поэтому в признаки включены `lag_24`, `lag_168`, календарные признаки и скользящее среднее за сутки.

## 4. Модели и подходы

### 4.1. Baseline-модели

В качестве простых ориентиров использованы сезонные прогнозы:

- `seasonal_naive_lag_24` — прогноз равен нагрузке в тот же час предыдущего дня;
- `seasonal_naive_lag_168` — прогноз равен нагрузке в тот же час предыдущей недели.

Также обучена линейная регрессия на семи табличных признаках. Она позволяет оценить, насколько далеко можно продвинуться с простой интерпретируемой моделью.

На test-выборке MAE сезонных baseline составила `60,75` для `lag_24` и `61,30` для `lag_168`; линейная регрессия улучшила результат до `58,19`.

### 4.2. Улучшенные модели

В экспериментах проверены ансамблевые модели:

- `RandomForestRegressor`;
- `HistGradientBoostingRegressor` в обёртке `MultiOutputRegressor`.

Для обеих моделей проведён небольшой подбор гиперпараметров на validation-части. Лучшие параметры random forest:

```text
n_estimators=300
max_depth=16
min_samples_leaf=5
max_features=0.8
random_state=42
```

Для histogram gradient boosting лучший validation-результат получен при `max_iter=300`, `learning_rate=0.03`, `max_leaf_nodes=15`, `l2_regularization=0.1`. Для random forest проверены шесть конфигураций, для boosting — также шесть. Отдельный ablation-анализ признаков не проводился.

Таблица всех вариантов подбора сохраняется в `artifacts/models/tabular_tuning_results.csv`.

### 4.3. Нейросетевая модель

Дополнительно проверена модель PyTorch LSTM. На вход подаётся последовательность длиной 168 часов с одним числовым признаком, затем используются:

```text
LSTM(input_size=1, hidden_size=64)
Linear(64, 64)
ReLU
Linear(64, 24)
```

Значения нормализуются по среднему и стандартному отклонению train-части. Обучение завершилось по early stopping после 13 эпох. LSTM оказалась лучше простых baseline, но уступила настроенному random forest на test-выборке.

Параметры обучения LSTM:

- optimizer — Adam с `lr=1e-3`;
- loss-функция — MSE;
- batch size — `64` для train и `128` для validation/test;
- максимальное число эпох — `25`;
- early stopping — `patience=5`;
- scheduler и аугментации не использовались.

Все эксперименты, графики и итоговые таблицы находятся в `notebooks/model_experiments.ipynb`.

## 5. Экспериментальный протокол и результаты

### 5.1. Экспериментальный протокол

После формирования окон получено 8 259 примеров: `X_seq` имеет форму `(8259, 168, 1)`, `X_tab` — `(8259, 7)`, целевой массив `y` — `(8259, 24)`.

Выборка делится строго по времени, без shuffle:

- train — первые 70% окон, 5 781 пример;
- validation — следующие 15%, 1 239 примеров;
- test — последние 15%, 1 239 примеров.

Validation используется для сравнения моделей и подбора гиперпараметров. Test используется только для итоговой оценки. MAE, RMSE и sMAPE рассчитываются по всем 24 значениям прогноза для каждого окна в исходном масштабе `requests/hour`. Такое разбиение предотвращает утечку информации из будущего в прошлое.

После выбора конфигурации скрипт `python -m src.models.train` повторно обучает финальный random forest на первых 85% окон, то есть на объединении train и validation, не используя test.

### 5.2. Сравнение моделей

Итоговые метрики на test-выборке:

| Модель | MAE | RMSE | sMAPE, % | Комментарий |
|---|---:|---:|---:|---|
| `random_forest_tuned` | **45,02** | **67,03** | **46,49** | Финальная модель |
| `random_forest` | 45,84 | 68,23 | 47,16 | Базовые параметры |
| `hist_gradient_boosting_tuned` | 46,67 | 69,46 | 47,43 | Настроенный boosting |
| `hist_gradient_boosting` | 48,73 | 72,41 | 49,43 | Базовые параметры |
| `pytorch_lstm` | 49,52 | 75,44 | 51,39 | Нейросетевая модель |
| `linear_regression` | 58,19 | 82,67 | 58,27 | Простой ML-baseline |
| `seasonal_naive_lag_24` | 60,75 | 89,52 | 61,95 | Суточный baseline |
| `seasonal_naive_lag_168` | 61,30 | 91,77 | 63,22 | Недельный baseline |

Для выбранной модели validation-метрики равны: MAE `35,66`, RMSE `48,58`, sMAPE `49,45%`.

### 5.3. Выбор финальной модели

Финальной выбрана `random_forest_tuned`, так как она показала лучшие MAE, RMSE и sMAPE на test-выборке. Модель превосходит сезонные baseline и LSTM, быстро выполняет inference, не требует GPU и удобно сохраняется через `joblib`.

Компромисс решения — размер артефакта и ограниченная способность random forest экстраполировать значения за пределами обучающего распределения. Для учебного сервиса преимущества по качеству и простоте эксплуатации важнее этих ограничений.

## 6. Архитектура решения и сервис

### 6.1. Архитектура пайплайна

Пайплайн проекта:

```text
Calgary-HTTP raw log
    -> scripts/prepare_calgary_http.py
    -> data/processed/calgary_http_hourly.csv
    -> notebooks/model_experiments.ipynb и scripts/tune_tabular_models.py
    -> выбор конфигурации модели
    -> python -m src.models.train
    -> artifacts/models/random_forest_tuned.joblib
    -> src/models/predict.py
    -> src/service/main.py
    -> REST API
```

Для повторного обучения финальной модели используется команда:

```powershell
python -m src.models.train
```

### 6.2. API и endpoints

Сервис реализован на FastAPI:

- `GET /health` — проверяет наличие модели и подготовленных данных;
- `GET /demo-request` — возвращает готовое демонстрационное тело запроса: последнее доступное окно из 168 значений датасета, заканчивающееся на выбранном часу;
- `POST /predict` — возвращает прогноз на следующие 24 часа.

Пример запроса к `/predict`:

```json
{
  "last_timestamp": "2026-05-31T13:00:00",
  "requests": [33, 87, 192]
}
```

В реальном запросе массив `requests` должен содержать не менее 168 значений. Последний элемент соответствует времени `last_timestamp`.

Пример структуры ответа:

```json
{
  "model_path": "artifacts/models/random_forest_tuned.joblib",
  "last_timestamp": "2026-05-31T13:00:00",
  "horizon": 24,
  "forecast": [
    {
      "timestamp": "2026-05-31T14:00:00",
      "requests": 299.08
    }
  ]
}
```

Опциональный query-параметр `time_range`, например `13:00-14:00`, добавляет компактное поле `forecast_by_hour`.

### 6.3. Технологический стек

Основные технологии:

- Python 3.12;
- pandas и NumPy для обработки данных;
- scikit-learn и joblib для табличных моделей;
- PyTorch для эксперимента с LSTM;
- FastAPI, Pydantic и Uvicorn для API;
- matplotlib и JupyterLab для EDA;
- Docker для воспроизводимого запуска сервиса.

Локальный запуск:

```powershell
uvicorn src.service.main:app --reload
```

Запуск через Docker:

```powershell
docker build -t load-forecaster .
docker run --rm -p 8000:8000 load-forecaster
```

Swagger UI доступен по адресу `http://127.0.0.1:8000/docs`.

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи и наблюдаемость

Сервис логирует загрузку модели, получение запроса, длину входной истории, успешное завершение прогноза и исключения. Endpoint `/health` возвращает статус сервиса, пути к модели и данным, факт наличия файлов и горизонт прогнозирования.

### 7.2. Конфигурация

Пример переменных окружения находится в `configs/.env.example`:

```text
APP_HOST=0.0.0.0
APP_PORT=8000
LOG_LEVEL=INFO
MODEL_PATH=artifacts/models/random_forest_tuned.joblib
DATA_PATH=data/processed/calgary_http_hourly.csv
```

Без изменения кода можно выбрать модель, датасет, уровень логирования, адрес и порт приложения.

`MODEL_PATH`, `DATA_PATH` и `LOG_LEVEL` применяются при любом запуске. `APP_HOST` и `APP_PORT` считываются при запуске `python -m src.service.main`; в приведённых командах запуска через `uvicorn` и Docker адрес и порт задаются аргументами команды.

### 7.3. Безопасность

Проект не использует токены, пароли и персональные данные. В исходном открытом Calgary-HTTP логе адрес клиента заменён обезличенным маркером `local` или `remote`. В `.gitignore` добавлены `.env`, виртуальное окружение, Python-кэш и локальные файлы логов.

## 8. Ограничения и дальнейшая работа

Текущие ограничения:

- датасет относится к конкретному серверу и историческому периоду 1994–1995 годов;
- сервис принимает уже агрегированный временной ряд и не подключается напрямую к production-логам;
- отсутствуют автоматическое переобучение и мониторинг деградации качества;
- для прогноза требуется история как минимум за 168 часов;
- sMAPE чувствительна к часам с низкой или нулевой нагрузкой;
- крупные `.joblib`-артефакты целесообразно хранить через Git LFS или внешнее artifact storage.

Возможные улучшения:

- добавить walk-forward validation;
- сравнить CatBoost, LightGBM и дополнительные модели временных рядов;
- расширить календарные признаки месяцем, днём года и праздничными днями;
- добавить автоматизированные API-тесты на `pytest`;
- реализовать обработку новых логов, регулярное переобучение и мониторинг распределения входных данных;
- добавить метрики сервиса и мониторинг времени ответа.

## 9. Сценарий демонстрации на защите

Команды запуска и примеры запросов приведены в `project/README.md`. Сценарий демонстрации:

1. Показать структуру репозитория: `notebooks/`, `src/models/`, `src/service/`, `data/`, `artifacts/`.
2. Открыть `notebooks/model_experiments.ipynb`, показать EDA, временное разбиение и таблицу сравнения моделей.
3. Объяснить выбор `random_forest_tuned`: лучшая test-MAE `45,02`, запуск без GPU, простой inference.
4. Запустить сервис локально или через Docker по инструкции из `README.md`.
5. Проверить статус:

```powershell
curl http://127.0.0.1:8000/health
```

6. Получить демонстрационный запрос:

```powershell
$body = Invoke-RestMethod "http://127.0.0.1:8000/demo-request?hour=13"
```

7. Получить полный прогноз на 24 часа и компактное представление для выбранного диапазона:

```powershell
Invoke-RestMethod `
  -Uri "http://127.0.0.1:8000/predict?time_range=13:00-14:00" `
  -Method Post `
  -ContentType "application/json" `
  -Body ($body | ConvertTo-Json -Depth 5)
```

При демонстрации следует обратить внимание на использование реальной сохранённой модели, воспроизводимый Docker-запуск, понятный REST API и обоснованный выбор финального алгоритма по результатам экспериментов.
